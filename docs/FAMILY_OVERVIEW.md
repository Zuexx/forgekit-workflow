# The ForgeKit Family — Overview

Four repositories that share one AI development workflow while building for entirely different
technology stacks. This document explains what each is for, how they relate, and the decisions
that produced the arrangement. It is the only document that describes all four as one system;
every other document in the family describes one repository.

## The four repositories

| Repository | Builds | Visibility |
|---|---|---|
| `forgekit` | .NET 10 API + Next.js 16 app, generated with `dotnet new forgekit` | public |
| `forgekit-ios` | iOS app — Swift 6, SwiftUI, Xcode project generated by Tuist | public |
| `forgekit-android` | Android app — Kotlin, Jetpack Compose, AGP 9 | public |
| `forgekit-workflow` | Nothing. It owns the shared workflow and its specification | public |

The first three are starter kits: you fork one, rename the product, and diverge. The fourth is
not a starter — it is where the workflow itself lives.

## The problem the family solves

The AI development workflow — spec-driven planning, code-graph retrieval, a pre-push coverage
hook, and a preflight check that reports whether any of it actually works on this machine — was
built inside `forgekit` and was bound to .NET and Next.js in exactly three lines of one script.
Everything else about it knew nothing of any stack.

Keeping a copy of that workflow in each starter would have reproduced a failure this project had
just spent a release removing from its package versions: the same thing written in several
places, where an update reaches some of them and not the others. So the workflow moved to its own
repository, and the three starters consume it.

## How the sharing works

`forgekit-workflow` owns seven files. Each consuming repository adds it as a second git remote
and runs `pnpm sync-workflow`, which copies those files in and splices the shared OpenSpec rules
into the repository's own `openspec/config.yaml` below a marker line.

Shared, overwritten on every sync:

```
scripts/preflight.sh                          is the workflow operational here?
scripts/sync-workflow.sh                      the sync itself
.githooks/pre-push                            plans must cite OpenSpec task ids that resolve
.mcp.json                                     the CodeGraph MCP server
.claude/settings.json                         the Superpowers plugin
openspec/rules.yaml                           planning rules and operation guidance
openspec/specs/workflow-toolchain/spec.md     what the workflow must do
```

Owned by each repository, never touched by the sync: its `openspec/config.yaml` context block,
its `scripts/verify.sh`, its `package.json`, its `AGENTS.md`, and the product itself.

The mechanism is deliberately plain — a git remote and `git checkout`, the same idiom `forgekit`
already documents for syncing its shared API layer. Publishing the workflow as an npm package was
rejected: the git hook and the MCP declaration must be real files at fixed paths, so a copy step
survives either way, and the package would add release overhead without removing it.

## The stack declaration

`scripts/preflight.sh` is shared byte-for-byte across all four repositories. Everything about it
that varies by stack is declared by the consuming repository in `package.json`:

```jsonc
"forgekit": {
  "sourceGlobs":     ["*.swift"],            // what counts as source, for index freshness
  "requiredTools":   ["tuist", "xcodebuild"], // machine-level tools this stack needs
  "nodeSubprojects": []                       // nested npm projects with their own scripts
}
```

`sourceGlobs` names the *subject* of a measurement, so an empty one is a failure — falling back
to "every tracked file" would silently change what is being measured. `nodeSubprojects` only
*scopes* a search, so an empty one is a real answer and is reported rather than failed. That
distinction is written into the specification.

## The governing rule

One sentence shapes every check in this family:

> A check that cannot measure its subject must FAIL, never pass. An `ok` has to mean "I looked
> and it was fine", not "I found nothing to look at".

It is not decoration. Defects found by applying it, in this codebase, include: an empty hooks
directory reporting success; a citation check printing nothing when the instruction files had no
citations left; a declaration array silently losing its last entry so a one-element list read
back as empty; and a sync that reported a missing file, spliced from a stale local copy, and
exited zero.

## Why Godot is not in the family

CodeGraph — the retrieval layer the workflow depends on — ships extractors for 28 languages.
GDScript is not among them, so `codegraph_explore` returns nothing for a Godot project. The first
planning rule requires the Impact section of a proposal to be grounded in the graph rather than
in an estimate, and that rule cannot be satisfied where the graph is blind.

A native Godot setup therefore needs that rule replaced with something its ecosystem can actually
support — which makes it a separate design rather than a fourth starter. Using C# for Godot would
avoid the problem, since CodeGraph does index C#.
